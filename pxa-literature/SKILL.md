# literature — 文獻研究 SOP（階段一＋階段二）

> 📊 本 skill 套件內附 `pipeline-flowchart.html`——整條 pipeline 的一頁式流程圖。第一次使用或向他人說明時，先開這張圖。

把「原始文獻 → 閱讀研究 → 筆記整理與交互對照 → 高品質知識庫 → 工程文件草稿」固化為團隊可複製的流程。核心精神：**每個陳述可追溯到來源頁碼、每個概念只有一個家、每個階段有驗證關卡（gate）、階段推進須經使用者確認**。

## 前置需求與快速開始

**環境需求**：

| 項目 | 用途 | 備註 |
|------|------|------|
| `python3` | 跑 QA 腳本 `scripts/check_vault.py` | 僅用標準庫，無需額外安裝 |
| `pdftotext`（poppler）或 `pdfplumber` | 文字型 PDF 擷取 | 掃描型 PDF 才需 OCR／逐頁視覺閱讀；實務上透過 `pdf` skill 呼叫，Cowork 環境通常已備 |
| `doc-coauthoring`／`docx`／`pdf` skill | 階段二產出與轉檔（選用） | 未安裝時階段二改走一般分節迭代、轉檔可略過 |

**如何觸發**：把 PDF 放進 `source/`，用自然語言請 Claude 整理即可——例如「把 source/ 的文獻整理成 Obsidian 知識庫」「幫我做這批論文的文獻回顧」；描述命中即自動啟動，或直接點名 `literature` skill。

**最小起步**：

1. 建 `source/Paper/`，放 1–2 篇 PDF。
2. 對 Claude 說：「用 literature skill 把 source/ 的文獻整理進 vault」。
3. Claude 會依序：盤點（跑 `check_vault.py` 反查未建檔）→ 逐篇建 source note → 萃取原子筆記 → 建 MOC → QA gate。
4. **每階段結束會停下等你確認才續行**——這是刻意設計，不是卡住。

## 資料夾慣例

skill 假設專案根目錄具備以下結構（缺少的資料夾在開始前建立；`obsidian/` 為團隊慣用的 vault 名稱，若專案已有其他名稱的 Obsidian vault 則沿用之）：

> **命名說明**：`obsidian`（非 "obsidian"）為本團隊 vault 的既定資料夾名稱——vault 內筆記、腳本路徑與既有引用皆已沿用此名，改動成本高，故維持不變，**請勿「更正」為 obsidian**。若你的專案用其他 vault 名稱，全流程沿用你的名稱即可，腳本的 vault 路徑為參數傳入、不寫死。

```
<專案根>/
├── source/          # 【輸入】原始文獻，依類型分子資料夾：Paper / Textbooks / Lecture Notes / Thesis / Web Resources
├── obsidian/        # 【階段一輸出】Obsidian vault
│   ├── sources/     # 文獻筆記：每份文獻一則
│   ├── notes/       # 原子筆記：每個概念一則
│   ├── MOCs/        # 每主題一則索引頁
│   └── templates/   # 三種模板（首次建 vault 時從本 skill 的 templates/ 複製過去）
└── documents/       # 【階段二輸出】工程文件（.md 開發 → .docx/.pdf 交付）
```

研究主題因工程師而異，但流程不變——不要把特定主題的內容假設寫進流程。

## 總流程

```
階段一  source/ → obsidian/     （逐篇閱讀 → 三類筆記 → QA gate）
   ↓ 使用者確認
階段二  obsidian/ → documents/  （MOC 作大綱 → 工程文件草稿 → docx/pdf）
   ↓ 到此停止
使用者（工程師）介入：判讀哪些資料有用、決定後續（app / 正式報告）——不屬本 skill
```

每階段開始前用 TaskList 列出工作項；階段結束時以簡潔表格回報成果與 QA 結果。

## 階段一：source/ → obsidian/

### 1. 盤點與確認

列出 `source/` 內全部文獻，與 `obsidian/sources/` 現有筆記比對，產出「待處理清單」表格（含檔名、類型、大小、是否已有筆記）給使用者確認主題名稱與範圍後才開始。已有筆記的文獻不重做，除非使用者要求。

盤點的機械化依據是 `scripts/check_vault.py <vault> --source-dir <source路徑>`：它會反向比對並列出「未建檔文獻」（source/ 內存在但沒有任何 source note 的 `source_file` 指向它的檔案）。使用者事後補放新文獻時，同一檢查會在 QA gate 自動抓到漏網——所以任何時候執行本 skill，都要先跑一次此檢查作為盤點起點。

### 2. 逐篇閱讀 → source note（文獻筆記）

每份文獻一則，存於 `sources/`，用 `templates/source-note.md` 模板。閱讀 PDF 時使用 pdf skill 的擷取方法（文字型 PDF 用 pdftotext／pdfplumber；掃描型才考慮 OCR 或逐頁視覺閱讀）。大型教科書（>200 頁）不逐頁精讀——先讀目錄鎖定與主題相關的章節，只精讀該部分，並在筆記中註明涵蓋範圍。

**命名**：`年份 作者 - 短標題.md`（如 `1971 MacNeal - Hybrid CMS.md`）；網路資源與講義可用 `來源 - 短標題.md`。

**內容要求**：
- frontmatter 必填：`type: source`、`authors`、`year`、`title`、`source_file`（指向 `source/` 內實際檔案的相對路徑）、`created`、`status: draft`。
- 「重點摘錄」每條**必須帶頁碼或章節錨點**，如 `（Eq.14-15, p.7-8）`、`（§III.B）`。這是之後交互對照與抽驗的依據——沒有錨點的陳述等於不可驗證。
- 公式照原文轉寫為 LaTeX，**特別注意正負號、下標與係數**——這是最常出錯的地方。
- 「可衍生的原子概念」每條格式：`- [[原子筆記名]]（中文名） — 一句話描述`；若該概念決定不建原子筆記，則寫純文字 `- 中文名（English Term） — 描述`，不留空的 wikilink。
- 若某文獻與主題僅間接相關、決定不衍生原子筆記，在筆記中加「決策說明」一節記錄原因（決策要可追溯，之後的人才知道不是漏做）。

### 3. 萃取概念 → atomic note（原子筆記）

從 source notes 萃取概念清單，先向使用者確認清單（概念的粒度與取捨是研究判斷，不要擅自定案），再逐一建立於 `notes/`，用 `templates/atomic-note.md` 模板。範例見 `references/example-atomic-note.md`——**動筆前先讀它**，以下規則都以該範例為準：

**結構與內容**
- **一則筆記只講一個概念**（原子性）。若寫著寫著出現第二個概念，拆出去。
- **命名用概念名稱本身**（英文技術術語為主，如 `Component Mode Synthesis (CMS).md`），利於 wikilink 直觀；筆記內文以繁體中文為主、技術術語保留英文。
- 章節骨架：核心陳述 → 文獻回顧 → 符號表 → 數學形式 →（演算法/程序類概念加）演算法程序 → 關鍵要點 → 相關概念 → 來源。純定性概念可省略符號表與數學形式，但不得把公式塞回文字段落充數。
- 「相關概念」至少連結 1–2 則其他原子筆記，並一句話說明關係（連結密度是知識庫價值所在；孤立筆記等於沒寫）。
- 「來源」段回連 source note 並帶頁碼/章節。
- 同一概念出現在多份文獻時，把各文獻的觀點整合在同一則筆記（交互對照），不要一個概念多則筆記。

**撰寫風格（比照論文文獻回顧）**
- 「文獻回顧」一節以學術文獻回顧的口吻撰寫：以「作者 (年份) 提出／指出／證實」敘述，明確區分各文獻的貢獻、方法演進與彼此關係（誰奠基、誰延伸、誰驗證），論述問題設定的動機與方法的取捨理由。理論鋪陳要詳細嚴謹——寧可多寫兩段把前因後果講清楚，不要壓縮成條列。
- **公式與文本強制分離**：凡含等號、不等號或運算關係的數學式，一律獨立為 `$$...$$` display block 並以 `\tag{n}` 編號；行文中只允許出現單一符號（如 $\bar c$、$[M_R]$），禁止行內夾帶完整方程式。公式集中在「數學形式」一節，每條式前註明來源（文獻＋原文式號），行文以「見式 (n)」引用。
- 「符號表」以表格列出本筆記用到的全部符號與意義；每個符號在首次出現的段落或符號表中必須有定義。
- 演算法／流程類概念另立「演算法程序」一節，以編號步驟寫出可執行的程序，步驟中引用式號。

### 4. 建 MOC（每主題一則）

用 `templates/MOC.md`，存於 `MOCs/`，命名 `主題-MOC.md`。依理論脈絡（如：載荷來源 → 耦合 → 建模 → 驗證 → 最佳化）分節串接**全部**原子筆記，每條附一句話定位；文末回連全部 source notes。MOC 的章節結構同時就是階段二工程文件的大綱，編排時要以「能直接當文件目錄」的標準來寫。

### 5. QA gate（結構＋內容雙重驗證）

**結構驗證**——執行 `scripts/check_vault.py <vault路徑>`，須全數通過：

| 檢查項 | 標準 |
|--------|------|
| 斷鏈 wikilink | 0 |
| 孤兒筆記（無入鏈的原子筆記） | 0 |
| MOC 覆蓋率 | 全部 atomic + source notes 皆被 MOC 收錄 |
| 原子筆記出鏈 | 每則 ≥1 |
| frontmatter 完整性 | 必填欄位齊全 |
| source_file 路徑 | 指向實際存在的檔案 |

**內容抽驗**——至少抽 20%（最少 2 篇）source notes 回對 PDF 原文：核對頁碼錨點、公式（含正負號）、關鍵數據。發現錯誤即修正，並考慮同型錯誤是否散布在其他筆記（例如公式轉寫錯誤通常會複製到引用它的原子筆記）。

**status 升級**：`draft`（初稿）→ `reviewed`（結構驗證通過）→ `stable`（內容抽驗對照原文通過）。只有實際驗過的才升級，不要整批升級。

### 6. 階段一收尾

以表格回報：文獻數、三類筆記數、QA 結果、抽驗發現與修正。**向使用者確認後才進階段二。**

## 階段二：obsidian/ → documents/

### 1. 開發稿（.md）

- 以該主題 MOC 的章節結構為大綱，把原子筆記內容整合成**連貫敘事**（不是筆記的堆疊——散點要串成推導鏈，段落間要有邏輯過渡）。
- 撰寫過程採用 doc-coauthoring skill 的共筆流程：先向使用者確認文件目的、讀者與詳略深度，分節起草、逐節迭代。（若未安裝 doc-coauthoring，改走一般分節迭代：仍先確認目的/讀者/深度，再逐節起草交審。）
- 標準章節（依主題增減）：目的與範疇 → 理論背景 → 方法/推導 → 假設與限制 → 實作/驗證 → 結論 → 參考文獻。
- 參考文獻對應 source notes 的書目資訊；內文重要陳述保留來源標註（作者年份＋頁碼），維持可追溯性。
- 產出 `documents/主題.md`，交使用者審閱迭代。

### 2. 交付檔（.docx / .pdf）

使用者確認 .md 定稿後，依交付需求轉檔：`.docx`（需簽核/追蹤修訂）用 docx skill，`.pdf`（唯讀交付）用 pdf skill。轉檔前先讀對應 skill 的 SKILL.md。

### 3. 停止點

交付 .docx/.pdf 後**本 skill 的工作即結束**。明確告知使用者：接下來由工程師判讀資料的取捨，後續是否產出互動 app 或正式研究報告屬另外的討論——不要主動接續做階段三。

## 品質原則（貫穿全程）

1. **可追溯**：任何寫進筆記或文件的技術陳述，都要能沿「文件 → 原子筆記 → source note → 頁碼」找回原文。做不到就別寫進去。
2. **不確定就標註**：OCR 品質差、公式看不清、原文語意模糊時，在筆記中明確標記（如「⚠ 原文掃描不清，符號待確認」），不要猜。
3. **語言慣例**：內文繁體中文，技術術語、法規名稱、變數符號保留英文原文。
4. **簡潔回報**：進度與結果用表格，避免冗長敘述。
