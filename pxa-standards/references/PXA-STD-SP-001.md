本文件採用 ANSI/NISO Z39.18 與 DoD/NASA 技術標準規範語法：

| 關鍵字 | 英文原文 | 意義 | 約束力 |
|--------|---------|------|--------|

| **禁止** | shall not | 絕對禁止 | 強制 |
| **建議** | should | 強烈建議，除非有文件化正當理由 | 建議 |

## 1. 範圍

### 1.1 目的

本標準定義品翔航太（PXA）所有技術報告的分級、編號、審查、發行管控與證據品質之治理規則，確保跨專案、跨作者的報告品質一致性。

本標準為「治理規則的單一真實來源」；報告之結構、模板與格式規則歸 PXA-STD-SP-002。

### 1.2 適用範圍

| 類型 | 適用文件 |
|------|---------|
| **SP（標準）** | 公司標準、技術指南、手冊、範本（`PXA-STD-SP` 系列） |
| **SP（研究）** | 跨專案通用專題研究報告，建立規範性工程結論（`PXA-{TOPIC}-SP` 系列） |
| **TM** | 以 SP 研究報告為依據，針對具體專案問題進行工程推論的單主題報告 |
| **TP** | 整合多份 TM 或 SP，形成完整設計階段記錄的合成報告 |

本標準不適用於：提案文件、合約文件、內部備忘錄、會議紀錄。

## 2. 報告分級與信任鏈

### 2.1 報告類型

| 類型 | 系列 | 全稱 | 定義 | STRN 格式 | 審查等級 |
|:----:|:----:|------|------|-----------|----------|
| **SP（標準）** | `PXA-STD-SP` | Special Publication | 公司標準、技術指南、手冊、範本 | `PXA-STD-SP-{NNN}` | CTO 核准 |
| **SP（研究）** | `PXA-{TOPIC}-SP` | Special Publication | 跨專案通用的單一技術議題深度研究（NASA CR 風格完整研究報告），建立規範性工程結論，作為下游報告的單一真實來源；證據基礎為 vault | `PXA-{TOPIC}-SP-{YYYY}-{NNN}` | 同儕審查 |
| **TM** | `PXA-{PROJECT}-TM` | Technical Memorandum | 以 SP 研究報告為依據，針對具體專案/階段問題進行工程推論的單主題報告 | `PXA-{PROJECT}-TM-{YYYY}-{NNN}` | 內部技術審查 |
| **TP** | `PXA-{PROJECT}-TP` | Technical Publication | 整合多份已審核 TM 或 SP 的合成報告，含跨主題系統性分析與完整推導 | `PXA-{PROJECT}-TP-{YYYY}-{NNN}` | 同儕審查 |

### 2.2 分級判定

報告 **必須** 依以下準則分級（依序判定，符合即止）：

| # | 判定條件 | 類型 |
|:-:|---------|:----:|
| 1 | 公司級規範、標準、範本、手冊 | SP（標準） |
| 2 | 單一技術議題深度研究，結論跨專案通用（含完整公式推導） | SP（研究） |
| 3 | 整合多主題之合成報告；含系統性敏感度分析、獨立 V&V，或為設計審查正式交付物 | TP |
| 4 | 引用 SP 結論應用於具體專案問題；初步數據、工作文件或單一階段快速報告 | TM |

### 2.3 信任鏈與類型間關係

**單向信任鏈**：

```
vault（證據層，QA gate）→ SP（研究，CR 風格）→ 人工審核 → TM / TP / 設計報告（直接引用 SP）→ 人工審核
```

SP（研究）之證據基礎為 **obsidian vault**（§5.5）：其專案層證據角色（原由 TM 承擔者）由 vault 取代。下游 TM、TP 與設計報告 **可選** 直接引用 SP——TM 不是 TP 之必經素材層。

| 規則 | 說明 | 判定 |
|------|------|:----:|
| SP 證據基礎 | SP（研究）之文獻證據 **必須** 可追溯至 vault（原子筆記 → source note → PDF 頁碼） | [H] |
| SP 單一真實來源 | SP（研究）的工程結論 **必須** 被下游報告以 `[PXA-{TOPIC}-SP-{YYYY}-{NNN}, §X.Y]` 格式引用，不得重新推導 | [H] |
| TM 獨立性 | 每份 TM **必須** 可獨立閱讀、獨立審核、獨立發行 | [H] |
| 引用義務 | 核心工程假設或公式 **必須** 追溯至 SP 或外部文獻，不得無來源陳述 | [H] |
| TP 合成性 | TP **必須** 以多份已審核 TM 或 SP 為素材，由作者重新整合撰寫；**禁止** 直接拼接內容 | [H] |
| TP 追溯性 | TP **必須** 在前頁或本文中標註來源 TM/SP 編號與版本 | [H] |

### 2.4 SP（研究）產製要求

| 要求 | 說明 |
|------|------|
| 議題聚焦 | 每份 SP **必須** 聚焦於單一技術議題，不得混合多個領域主題 |
| 結論可引用性 | 核心結論 **必須** 明確標示於 Part 5（[C-n] 格式，SP-002 §3.6），格式符合下游引用需求 |
| TOPIC 對應 | STRN 中的 TOPIC 代碼 **必須** 與 §3.2 核准代碼一致 |
| 引用區辨 | 內部引用 `[PXA-{TOPIC}-SP-{YYYY}-{NNN}, §X.Y]` **必須** 與外部文獻引用 `[Author Year]` 在形式上可區分（`PXA-` 前綴為區分標記） |

### 2.5 Quick / Update 變體

每份 TM 或 TP **可選** 以兩種變體發行：

| 變體 | 定義 | 篇幅 | 適用時機 |
|------|------|------|----------|
| **Quick（快速版）** | 骨架＋核心結果，含 `[TBD]`/`⚠ 待深化` 標記 | ~3,000–5,000 字 | 初版快速產出、階段性進度回報 |
| **Update（完整版）** | 敘事完整，所有標記已解消，可正式交付 | ~8,000–15,000 字 | 審查提交、基線發行 |

**裁剪規則**——Quick 版 **必須** 保留：

| 項目 | 說明 |
|------|------|
| 前頁 | 封面＋書名頁＋DAA＋文件資訊＋修訂紀錄 |
| Part 1 | 完整摘要總覽 |
| Part 2 | 至少 §2.1＋§2.2 |
| Part 3 | 所有輸入與假設 |
| Part 4 | 每主題：公式＋符號表＋計算結果（敘事可標「⚠ 待深化：{說明}」） |
| Part 5 | 結論（至少 §5.1） |
| Part 6 | §6.1 參數基線（完整）＋§6.4 合規矩陣 |
| 附錄 | A（RTM 框架）＋E（參考文獻） |

其餘區段 Quick 版 **可選** 省略或簡化；Update 版 **必須** 完整、無「⚠ 待深化」殘留 [S]。

### 2.6 產製模式與交付格式

報告以 Markdown 為單一真實來源（SSoT），結構依 PXA-STD-SP-002。**正式交付格式為 docx**：Report.md 通過合規 gate 後，以 scribe skill 之確定性轉換管線（pandoc＋`SP-reference.docx` 樣式範本＋`md2docx.py`）產出 `{STRN}.docx`——同一份 MD 永遠轉出同一版面；公式轉為 Word 原生方程式（OMML）、式號保留。PDF 需要時由 docx 另存。

| 規則 | 說明 | 判定 |
|------|------|:----:|
| MD 為 SSoT | 內容修訂 **必須** 回 MD 端修改後重轉，**禁止** 只改 docx | [H] |
| 轉換確定性 | docx **必須** 由轉換腳本產出，**禁止** 手工重排版面（版面調整改範本） | [H] |

原 LaTeX 交付路徑（CLU-SP-004）已退役歸檔；latexer skill 規劃取消。

| 模式 | 輸入 | 本文結構 |
|:----:|------|----------|
| **SP 研究** | 單一 SP.md | Part 1–6（SP-002 §3，SP 欄） |
| **TM 獨立** | 單一 TM.md | Part 1–6 為頂層 |
| **TP 合成** | 多個已審核 TM/SP.md | Executive Summary＋章節（各章含 Part 1–6） |

## 3. 報告編號（STRN）

三種格式均以 ANSI/NISO Z39.23 為基礎，裁剪為連字號分隔以相容檔案系統。

### 3.1 三種格式

**SP（標準）**：

```
PXA-STD-SP-{NNN}
├── PXA-STD    固定前綴（PXA 標準系列）
└── SP-{NNN}   流水號三碼（001, 002, ...）
```

**SP（研究）**：

```
PXA-{TOPIC}-SP-{YYYY}-{NNN}
├── PXA      組織代碼（固定）
├── {TOPIC}  技術領域代碼（§3.2）
├── SP       類型
├── {YYYY}   4 位西元年
└── {NNN}    3 位流水號，年度歸零
```

**TM / TP**：

```
PXA-{PROJECT}-{TYPE}-{YYYY}-{NNN}
├── {PROJECT}  專案代碼（2-6 字元大寫）
└── {TYPE}     TM 或 TP
```

### 3.2 TOPIC 代碼

| 代碼 | 領域 | 範例 STRN |
|:----:|------|-----------|
| `AERO` | 氣動力學 | `PXA-AERO-SP-2026-001` |
| `STRUCT` | 結構 | `PXA-STRUCT-SP-2026-001` |
| `GNC` | 導引、導航與控制 | `PXA-GNC-SP-2026-001` |

TOPIC 代碼由 CTO **核准** 後方可新增。

### 3.3 本地後綴（選用）

本地後綴以 `+` 分隔，附加於序號群之後。適用於 SP（研究）、TM、TP；SP（標準）不使用。

| 後綴類型 | 格式 | 範例 |
|---------|------|------|
| 版本 | `+v{M}-{N}` | `+v1-0`、`+v2-1` |
| 設計階段 | `+{PHASE}{X}` | `+DP3`、`+SP2` |
| 狀態 | `+DRAFT`、`+REVIEW`、`+BASELINE` | `+DRAFT` |
| 修訂 | `+Rev{X}` | `+RevA` |
| 卷冊 | `+Vol{X}` | `+Vol2` |

多重後綴 **必須** 以 `+` 串接，順序為：版本 → 階段 → 狀態。

### 3.4 範例

| 報告編號 | 類型 | 說明 |
|---------|:----:|------|
| `PXA-STD-SP-001` | SP（標準） | PXA 技術報告治理標準 |
| `PXA-AERO-SP-2026-001` | SP（研究） | 氣動力學專題研究第 1 號 |
| `PXA-GNC-SP-2026-002+v1-0` | SP（研究） | GNC 專題研究第 2 號，版本 1.0 |
| `PXA-OSP-TM-2026-003+v1-0+DP3` | TM | Osprey 專案 TM，版本 1.0，設計階段 DP-3 |
| `PXA-OSP-TP-2026-001+v2-0` | TP | Osprey 專案 2026 年第 1 份 TP，版本 2.0 |

### 3.5 標示位置

報告編號 **必須** 出現於：封面右上角、書名頁右上角、每頁頁首、DAA §I 文件識別欄。

### 3.6 編號登記表

每個專案 **必須** 維護一份編號登記表，防止重號：

| 編號 | 標題 | 作者 | 日期 | 狀態 |
|------|------|------|------|------|
| `PXA-OSP-TM-2026-001` | 需求分析 | 張○○ | 2026-01-15 | 基線 |

### 3.7 版本規則

| 情境 | 版本變更 | 範例 |
|------|----------|------|
| 首版 | v1.0 | 初版發行 |
| 小幅修正（錯字、格式、數值微調） | 次版號 +1 | v1.0 → v1.1 |
| 重大變更（結構變更、設計點變更） | 主版號 +1，次版歸零 | v1.3 → v2.0 |

## 4. 審查與發行管控

### 4.1 審查等級

| 報告類型 | 最低審查等級 | 審查人 |
|:--------:|------------|--------|
| **SP（標準）** | CTO 核准 | CTO |
| **SP（研究）** | 同儕審查 | 至少一位**非作者**的合格技術人員 |
| **TM** | 內部技術審查 | 專案內技術主管或 PM |
| **TP** | 同儕審查 | 至少一位**非作者**的合格技術人員 |

### 4.2 審查檢核項

技術審查 **必須** 至少涵蓋（參照 NASA SP–7602 Appendix B）：

| # | 檢核項 | 適用 |
|---|--------|------|
| 1 | 報告撰寫清晰，邏輯通順 | 全類型 |
| 2 | 所有編號項（圖、表、公式、參考文獻、附錄）依序引用且編號正確 | 全類型 |
| 3 | 無拼寫、文法、標點錯誤 | 全類型 |
| 4 | 結論由正文資料支持 | 全類型 |
| 5 | 引用文獻可識別且資訊充分 | 全類型 |
| 6 | 圖表數據清晰一致 | 全類型 |
| 7 | 符合資訊安全與出口管制要求 | 全類型 |
| 8 | 完整公式推導可驗證 | SP（研究）＋TP |
| 9 | 敏感度分析覆蓋主要參數 | 僅 TP |
| 10 | V&V 方法與結果可追溯 | 僅 TP |

### 4.3 審查結果等級

| 等級 | 英文 | 判定條件 | 處置 |
|------|------|----------|------|
| **A** | Accept | 所有必須項通過，建議項無重大缺失 | 直接放行，進入 DAA 簽核 |
| **B** | Accept with Minor Correction | 必須項全數通過，但 ≤ 3 項建議/可選缺失或格式瑕疵 | 作者修正後免重審，審查者確認即可 |
| **C** | Major Revision Required | 任一必須項未通過，或 > 3 項建議缺失 | 作者修正後重新送審 |

**判定規則**：必須項未通過自動判 C；可選項缺失不影響等級；Quick 版之「⚠ 待深化」標記不計為缺失。

**審查紀錄格式**：

```markdown
| 審查項 | 結果 | 備註 |
|--------|:----:|------|
| {檢核項} | ✓ / ✗ | {修正說明} |

**審查結果**：{A / B / C}
**審查者**：{姓名} / {日期}
```

### 4.4 安全分級

PXA 報告 **必須** 依三級分類：

| 等級 | 定義 | 發行範圍 |
|------|------|----------|
| **公開** | 不含敏感資訊，可公開發行 | 無限制 |
| **內部** | 含公司內部技術資訊 | 專案團隊＋組織內部（含授權承包商） |
| **限制** | 含出口管制、智慧財產或客戶機密資訊 | 具名授權人員，須經 CTO 核准 |

### 4.5 文件發行授權（DAA）

DAA 為 PXA 報告的發行管控機制，參照 NASA NF-1676 精神與 AR 70–31 資訊保護原則，裁剪為民間組織簡化版。DAA **必須** 包含五區段（表單模板見 SP-002 §7）：

| 區段 | 內容 | 填寫時機 | 負責人 |
|------|------|----------|--------|
| **§I 文件識別** | 標題、編號、作者、版本、日期、專案 | 產出時自動填入 | 撰寫者 |
| **§II 分類與發行** | 安全等級、出口管制、發行範圍、智慧財產 | 作者審閱後 | 文件作者 |
| **§III 作者聲明** | 確認內容分類正確性 | 作者審閱後 | 文件作者 |
| **§IV 審查與核准** | 技術審查 → 管理審查 → CTO 核准 | 審查流程 | 審查鏈 |
| **§V 處置** | 存檔、發送、公開 | 核准後 | 文管人員 |

### 4.6 出口管制

涉及出口管制技術之報告，**必須** 於封面、書名頁、DAA §II 標示管制類別。PXA 工程師 **建議** 諮詢法務確認是否涉及 ITAR/EAR 或我國相關出口管制法規。

## 5. 證據與來源品質

品質標記共兩套系統＋一個行文旗標，各回答一個問題：

| 系統 | 標記 | 回答的問題 | 定義 |
|------|------|-----------|:----:|
| 文獻層級 | L1 / L2 / L3 | 引用來源的權威程度？ | §5.1 |
| 信度 | ★★★ / ★★ / ★ / ⚠ | 這個數值/結論有多可靠？ | §5.2 |
| 佐證旗標 | ✓ / ⚠ | 這個論點有沒有交叉確認？（行文旗標，併入 ★ 判定） | §5.2 |

> 原 E1–E4 證據等級系統已廢除（v3.0）——其資訊已由 ★ 判定條件涵蓋。

### 5.1 文獻層級

引用文獻 **必須**（SP 研究/TP）/ **建議**（TM）標註文獻層級：

| 層級 | 定義 | 範例 |
|------|------|------|
| **L1** | 專案內文件（可完整追溯） | PXA 內部 SP/TM/TP、測試報告 |
| **L2** | 教科書、同行審查文獻，或經機構技術審查之正式出版品 | Raymer、Roskam、AIAA Journal；NASA TM/TP/CR（裁定：一律 L2） |
| **L3** | 補充參考（非同行審查） | 技術手冊、供應商數據、線上資源、課程講義（如 Okawa、MIT OCW） |

### 5.2 信度與佐證

**佐證旗標**（行文中，Part 4 驗證比較用）：`✓`＝≥ 2 個獨立來源或方法交叉確認；`⚠`＝單一來源或缺佐證（**必須** 說明風險，缺口列入 TBD 清單）。

**信度判定樹**（依序檢查，符合第一個條件即停止）：

| 條件 | 信度 |
|------|:----:|
| IF 實測數據 AND 多來源交叉驗證（✓） | ★★★ |
| IF 實測數據 AND 無交叉驗證（⚠） | ★★ |
| IF 教科書理論 AND 案例驗證（✓） | ★★ |
| IF 教科書理論 AND 無案例驗證 | ★ |
| IF 單一文獻 OR 工程估算 | ★ |
| IF 假設值 OR 待驗證 | ⚠ |

**vault status 對映**（SP 研究適用）：

| vault status | 意義 | 佐證旗標 | [C-n] 信度上限 |
|--------------|------|:----:|:----:|
| `stable` | 內容經逐式對照 PDF 原文核驗 | ✓ | ★★（★★★ 仍須實測＋多來源） |
| `reviewed` | 結構驗證通過、內容未逐式核驗 | ⚠ | ★ |
| 筆記內含 ⚠ 標註 | 原刊存疑或無法核驗 | ⚠＋沿用存疑說明 | ⚠ |

### 5.3 狀態標記

| 標記 | 意義 | 使用情境 |
|:----:|------|----------|
| PASS | 滿足約束，裕度 ≥ 10% | 合規矩陣 |
| WARN | 滿足約束，裕度 < 10% | 合規矩陣 |
| FAIL | 不滿足約束 | 合規矩陣 |
| TBD | To Be Determined（數值不存在，待決定） | 待決清單 |
| TBC | To Be Confirmed（數值存在，待確認） | 待決清單 |

**狀態燈判定**（Part 1 §1.2）：達成且裕度 ≥ 10% → 🟢；達成但裕度 < 10%、有附加條件、TBD 待驗證、或未達成但有緩解方案 → 🟡；未達成且無緩解方案 → 🔴。

**風險等級判定**（Part 6 §6.7）：L × C（各 1–5）：1–4 低；5–9 中；10–25 高。

### 5.4 可追溯性與假設管理

| 規則 | 說明 | 判定 |
|------|------|:----:|
| 參數追溯 | 每個參數 **必須** 標註來源（上游階段/文獻/供應商/計算） | [H] |
| 決策追溯 | 每個設計決策 **必須** 標註理由與替代方案 | [H] |
| 需求追溯 | 每個需求 **必須** 可追溯至上游來源與下游驗證 | [H] |
| 假設管理 | 每個假設 **必須** 標註類型（✓ 已驗證 / TBC 待驗證 / Design 設計假設）與驗證狀態 | [H] |

### 5.5 Vault 證據鏈（vault-based evidence chain）

obsidian vault 為 PXA 之**正式證據層**：以 Obsidian 知識庫承載文獻研究成果（source note → atomic note → MOC），每個技術陳述具備頁碼級追溯錨點，並經雙重 QA gate 驗證（結構驗證 `check_vault.py`＋內容抽驗回對 PDF 原文）。

| 規則 | 說明 | 判定 |
|------|------|:----:|
| 追溯鏈 | SP（研究）之每個技術陳述 **必須** 可沿「報告 → 原子筆記 → source note → PDF 頁碼」找回原文 | [H] |
| status 分級 | `draft`（初稿）→ `reviewed`（結構驗證通過）→ `stable`（逐式核驗通過）；對映見 §5.2 | — |
| SSoT 迴寫 | 撰寫中發現 vault 錯誤 **必須** 先修 vault 再寫報告，**禁止** 只在報告端修正 | [H] |
| L2 協調制 | SP（研究）文獻回顧之 L2 ≥ 5 為**建議**目標而非硬性門檻：vault QA gate 已保證證據品質，L2 數量緊繃時 **必須** 回報使用者裁量，**禁止** 沉默帶過 | [S]（計數回報） |

## 6. 數值規範

| 規則 | 說明 |
|------|------|
| 有效位數預設 | 3 位有效數字（除非 Profile 另有規定） |
| 單位制 | SI 制為主；航空慣用單位（ft, kts, lb）**可選** 並列 |
| 常數 | 專案通用常數定義於 Profile（如 g, ρ₀, ν₀），正文 **禁止** 自行定義不一致的值 |
| 無因次量 | 2–3 位有效數字 |
| 百分比 | 2 位有效數字 |

學科特定數值規範 **必須** 定義於專案 Profile，本標準不重複定義。

## 7. 取捨研究格式

當存在多個候選方案時，**必須** 使用以下格式：

```markdown
#### 方案選擇：{主題名稱}

**問題陳述**：{一句話說明需要決定什麼}

**評估標準**：
| 標準 | 權重 | 理由 |
|------|:----:|------|

**候選方案**：
| 方案 | 優點 | 缺點 | 適用情境 |
|------|------|------|----------|

**評分矩陣**：
| 方案 | 標準1 | 標準2 | 標準3 | 加權總分 |
|------|:-----:|:-----:|:-----:|:--------:|

**選定方案**：{方案名稱}
**選定理由**：{2–3 句量化支撐}
**放棄方案**：{方案及原因}
**重新評估條件**：{觸發條件}
```

| 規則 | 說明 |
|------|------|
| 候選方案 | **必須** ≥ 2 個 |
| 評估標準 | **必須** ≥ 3 個，權重總和 = 100% |
| 選定理由 | **必須** 量化支撐（句型：「選定 X，因其在 Y 指標上優於 Z 達 N%」） |
| 重新評估 | **必須** 定義觸發條件 |

## 9. 修訂與發佈紀律

1. 任何規則變更 **必須** 落在 STD 正本（版本遞增＋版本紀錄行，依 §3.7），**禁止** 只改 SKILL.md 或下游 skill。
2. 修訂後同步：pxa-standards SKILL.md 之裁定表與版本表、前頁工具版本表（SP-002 §7）、scribe skill 之章節引用。
3. 新裁定流程：先記入 `documents/SP-series-map.md` 裁定紀錄（即時生效）→ 修訂對應 STD 文件 → 同步。
4. [S] 規則之新增/變更 **必須** 同步修訂 `check_sp.py`——腳本與條文不一致時以條文為準並立即修腳本。
5. 修訂涉及上位標準解讀時，**必須** 回查 skill `raw/` 原文，不憑記憶。
6. 歷史版本與退役文件存 `documents/reference/archive/`。
