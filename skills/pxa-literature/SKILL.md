# literature — 文獻研究 SOP v3.2（階段一＋階段二）

> 📊 本 skill 套件內附 `pipeline-flowchart.html`——整條 pipeline 的一頁式流程圖。第一次使用或向他人說明時，先開這張圖。
> 📋 版本變更明細見 `CHANGELOG.md`（v3 逐項對應審查發現；v3.1 新增「工程實踐」；v3.2 新增 PDF 分流閘門與成本控制原則）。

把「原始文獻 → 閱讀研究 → 筆記整理與交互對照 → 高品質知識庫 → 工程文件草稿」固化為團隊可複製的流程。核心精神：**每個陳述可追溯到來源頁碼、每個概念只有一個家、每份文獻經過批判評估、衝突不默默擇一、每個階段有驗證關卡（gate）、階段推進須經使用者確認。**

v3 的定位轉變：v2 保證「寫進 vault 的每個字可追溯且格式正確」；v3 進一步要求「該萃取的精華都被萃取、被批判性評估、被綜合成可支撐工程決策的比較與結論」——即從**文獻管理 SOP** 升級為**研究 SOP**。

## 前置需求與快速開始

**環境需求**：

| 項目 | 用途 | 備註 |
|------|------|------|
| `python3` | 跑 `scripts/check_vault.py`、`scripts/pdf_probe.py` | 僅用標準庫 |
| `pdftotext`（poppler）或 `pdfplumber`／`pypdf` | PDF 分流閘門與文字型擷取 | `pdf_probe.py` 優先用 poppler，缺時回退 pypdf |
| `pdf` skill（官方） | **掃描型／混合型 PDF 的 OCR** 分支執行者 | 分流閘門判定 scanned/hybrid 時委派它；無安裝則標記待人工 OCR |
| PDF 頁面渲染（pdf skill / `pdftoppm`） | 公式視覺核對 | 只渲染**選定深讀章節內要轉寫公式的那幾頁**，非全文，見「公式轉寫規則」 |
| `doc-coauthoring`／`docx`／`pdf` skill | 階段二產出與轉檔（選用） | 未安裝時階段二改走一般分節迭代、轉檔可略過 |

**腳本執行慣例（重要）**：本 skill 的腳本（`check_vault.py`、`pdf_probe.py`）住在 **skill 自身目錄**（載入本 skill 時系統告知的 base directory，下文以 `<skill根>` 代稱）。執行時一律用完整路徑 `python3 <skill根>/scripts/xxx.py …`，**禁止把腳本複製進使用者的專案資料夾**——專案資料夾是使用者的研究資料，skill 工具檔滲進去會污染 repo 與 Obsidian vault（曾實際發生：專案根莫名多出 check_vault.py）。同理，QA 結果以對話表格回報即可，**勿在專案根落地 vault_report.txt 之類的輸出檔**；確需留檔時放 `obsidian/.qa/` 並先告知使用者。

**如何觸發**：把 PDF 放進 `source/`，用自然語言請 Claude 整理即可——例如「把 source/ 的文獻整理成 Obsidian 知識庫」「幫我做這批論文的文獻回顧」；描述命中即自動啟動，或直接點名 `literature` skill。

**最小起步**：

1. 建 `source/Paper/`，放 1–2 篇 PDF。
2. 對 Claude 說：「用 literature skill 把 source/ 的文獻整理進 vault」。
3. Claude 會依序：研究框架確認 → 盤點（跑 `check_vault.py` 反查未建檔＋跑 `pdf_probe.py` 分流每份 PDF）→ Pass 1 全批略讀 triage → Pass 2 依分流路由逐篇深讀建 source note → 萃取原子筆記 → 建 MOC＋綜合層 → QA gate。
4. **每階段結束會停下等你確認才續行**——這是刻意設計，不是卡住（無人值守模式見文末）。

## 資料夾慣例

skill 假設專案根目錄具備以下結構（缺少的資料夾在開始前建立；`obsidian/` 為團隊慣用的 vault 名稱，若專案已有其他名稱的 Obsidian vault 則沿用之）：

> **命名說明**：`obsidian` 為本團隊 vault 的既定資料夾名稱——vault 內筆記、腳本路徑與既有引用皆已沿用此名，改動成本高，故維持不變，**請勿「更正」為其他名稱**。若你的專案用其他 vault 名稱，全流程沿用你的名稱即可，腳本的 vault 路徑為參數傳入、不寫死。

```
<專案根>/
├── source/          # 【輸入】原始文獻，依類型分子資料夾：Paper / Textbooks / Lecture Notes / Thesis / Web Resources
├── obsidian/        # 【階段一輸出】Obsidian vault
│   ├── sources/     # 文獻筆記：每份文獻一則
│   ├── notes/       # 原子筆記：每個概念一則（含每主題一則「符號慣例」筆記）
│   ├── MOCs/        # 每主題一則索引頁（含綜合層：比較矩陣、SOTA、gap）
│   └── templates/   # 三種模板（首次建 vault 時從本 skill 的 templates/ 複製過去）
└── documents/       # 【階段二輸出】工程文件（.md 開發 → .docx/.pdf 交付）
```

研究主題因工程師而異，但流程不變——不要把特定主題的內容假設寫進流程。

## 總流程

```
研究框架確認（主題＋研究問題 RQ＋工程決策需求）
   ↓
階段一  source/ → obsidian/
   盤點：check_vault 反查未建檔 ＋ pdf_probe 分流每份 PDF（text/hybrid/scanned＋large）
   Pass 1：全批略讀 → triage 表（seminal/derivative、關聯 RQ、分群、優先序）
   Pass 2：依群逐篇深讀 → source note（含批判評估＋涵蓋自評）
   → atomic note（交互對照＋衝突處理＋符號對映）
   → MOC＋綜合層（比較矩陣、SOTA 評述、gap 識別）
   → QA gate（結構＋內容雙重驗證）
   ↓ 使用者確認
階段二  obsidian/ → documents/  （MOC 作大綱 → 工程文件草稿 → docx/pdf）
   ↓ 到此停止
使用者（工程師）介入：判讀哪些資料有用、決定後續（app / 正式報告）——不屬本 skill
```

每階段開始前用 TaskList 列出工作項；階段結束時以簡潔表格回報成果與 QA 結果。

## 階段〇：研究框架確認（v3 新增）

開工前先與使用者確立**研究框架**，這是所有萃取取捨的依據：

1. **主題名稱與範圍**（同 v2）。
2. **研究問題（RQ）**：以編號列出本輪要回答的問題，如 `RQ1: INDI 與 NDI 在致動器動態顯著時的 robustness 差異`。沒有明確 RQ 時，由 Claude 依 source/ 內容起草 2–4 條候選 RQ 交使用者裁定。
3. **工程決策需求**：這批文獻要支撐什麼決策（選方法？定架構？寫認證論據？）——決定綜合層（比較矩陣）的欄位設計。

**萃取判準**（原子筆記取捨不再全丟給使用者，先以下列判準提案再交裁定）：與至少一條 RQ 相關；可跨文獻複用（≥2 份文獻觸及，或單一文獻但為 RQ 核心）；能支撐工程決策或後續推導。不合判準者留在 source note 的重點摘錄即可，不升格為原子筆記。

無人值守時：自行草擬 RQ 與判準，記錄於 MOC「研究框架」節並標注「未經使用者確認」，續行。

## 階段一：source/ → obsidian/

### 1. 盤點與確認

列出 `source/` 內全部文獻，與 `obsidian/sources/` 現有筆記比對，產出「待處理清單」表格（含檔名、類型、大小、是否已有筆記）。已有筆記的文獻不重做，除非使用者要求。

盤點的機械化依據是 `python3 <skill根>/scripts/check_vault.py <vault> --source-dir <source路徑>`（腳本從 skill 目錄執行，不複製進專案）：它會反向比對並列出「未建檔文獻」。任何時候執行本 skill，都要先跑一次此檢查作為盤點起點。

**PDF 分流閘門（v3.2 新增，深讀前必跑）**：來源 PDF 的本質（文字型／掃描型）你無法事先掌握，而「該用文字層擷取還是渲染影像」是 token 成本差一個數量級的決策——不能交給模型臨場猜。開工前對整個 `source/` 跑一次：

```
python3 <skill根>/scripts/pdf_probe.py source/ --json obsidian/.pdf-manifest.json
```

它量測每份 PDF 的文字層覆蓋率，確定性地判定分類並輸出**強制路由**，Pass 1／Pass 2 一律依此路由讀取（不自行改路）：

| 分類 | 判準 | 讀取路由 |
|------|------|---------|
| `text` | 文字層覆蓋 ≥ 0.85 | 文字層擷取（pdftotext/pdfplumber）；**不得整份渲染影像** |
| `hybrid` | 0.15 < 覆蓋 < 0.85 | 有文字層頁走文字擷取；`image_pages` 清單交 `pdf` skill OCR 後併入 |
| `scanned` | 文字層覆蓋 ≤ 0.15 | 整份委派 `pdf` skill 做 OCR → 產生文字層後再走文字擷取 |
| 疊加 `large` | 頁數 > 200 | 先以目錄／章節定位，**只深讀 triage 選中章節**，勿整份深讀 |

此閘門同時保品質（掃描件不會被當文字層擷取而產出亂碼）與控成本（影像渲染只發生在 OCR 與公式核對的必要頁）。manifest 的 `large` 檔案在 Pass 1 的「預估深讀範圍」欄一律標為特定章節。

### 2. Pass 1 — 全批略讀與 triage（v3 新增）

**深讀之前，先用低成本掃過全部待處理文獻**（每篇只讀摘要、引言末段、結論、圖表標題），產出 **triage 表**：

| 欄位 | 說明 |
|------|------|
| 檔名／類型 | 對應 source/ 檔案 |
| 定位 | seminal（奠基）／derivative（延伸）／survey（綜述）／application（應用案例） |
| 關聯 RQ | 對應哪幾條研究問題（可多條；無關聯者標記並建議降級或退回 scout） |
| 分群 | 依子題聚類（如：控制律／致動器建模／驗證方法） |
| 優先序 | 深讀順序：同群內 seminal → derivative；survey 最先讀（快速建圖） |
| 預估深讀範圍 | 全文／特定章節（`pdf_probe` 標 `large`（>200 頁）者——不分教科書或 paper/thesis/report——一律鎖定特定章節，不深讀全文） |

triage 表交使用者確認後才進 Pass 2。**深讀順序依 triage**，不依檔名排序——先讀奠基文獻，後讀延伸文獻，交互對照才有基準。

### 3. Pass 2 — 逐篇深讀 → source note（文獻筆記）

每份文獻一則，存於 `sources/`，用 `templates/source-note.md` 模板。**讀取路徑一律依 `pdf_probe` manifest 的分類**：`text` 走文字層擷取（pdftotext／pdfplumber）；`scanned` 先交 `pdf` skill OCR 得文字層再擷取；`hybrid` 文字頁走文字層、`image_pages` 交 OCR 併入——不因當下方便而改走整份影像渲染。`large` 檔（>200 頁，含 paper/thesis/report）依 triage 表鎖定章節精讀，並在筆記中註明涵蓋範圍。

**命名**：`年份 作者 - 短標題.md`（如 `1971 MacNeal - Hybrid CMS.md`）；網路資源與講義可用 `來源 - 短標題.md`。

**內容要求**：

- frontmatter 必填：`type: source`、`authors`、`year`、`title`、`venue`（期刊/會議/出版社）、`bibkey`（如 `raveh1999trim`，供階段二與 scribe 產參考文獻）、`source_file`（指向 `source/` 內實際檔案的**相對路徑**，如 `source/Paper/x.pdf`）、`created`、`status: draft`、`verified: none`。選填但強烈建議：`doi`、`volume_pages`。
- 「重點摘錄」每條**必須帶頁碼或章節錨點**，如 `（Eq.14-15, p.7-8）`、`（§III.B）`——此規則由 `check_vault.py` 機械檢查，無錨點視為 QA 失敗。
- **公式轉寫規則（v3 強化；v3.2 限縮渲染範圍）**：公式照原文轉寫為 LaTeX，特別注意正負號、下標與係數。**轉寫依據不得只有文字層擷取**——須以頁面渲染影像視覺核對後才可寫入筆記；文字層（pdftotext）只作為初稿輔助。但渲染影像**只針對「選定深讀章節內、當下實際要轉寫公式的那幾頁」**逐頁核對，**不得**為了找公式而整份或整章渲染成影像（那是 token 爆量的主因）。要轉哪條公式、才渲染那一頁。
- **批判評估（v3 新增）**：每則 source note 必含「批判評估」一節，載明——
  - `evidence_level`（frontmatter 亦填）：`L1` 理論推導／`L2` 數值模擬／`L3` 實驗（風洞、HIL、台架）／`L4` 飛行測試。多層並存取最高層並註明範圍。
  - 方法有效性：假設是否合理、實驗/模擬設計是否支撐結論、樣本或案例是否足夠。
  - 限制與適用邊界：作者自承的與你判讀出的都要寫，並區分之。
  - 可信度評語：一句話結論（如「結論可信但僅驗證於低速剛性構型，外插至彈性機體須保留」）。
- **涵蓋自評（v3 新增，recall 可追溯）**：列出該文獻的章節／主要貢獻清單，逐項標記「已萃取（→ 指向摘錄或原子筆記）／未萃取（＋原因，如：超出 RQ 範圍）」。QA 的完整性抽驗以此為對照基準。
- **工程實踐（v3.1 新增）**：每則 source note 必含「工程實踐」一節（位於「我的評註」之後），為工程師後續 coding／Simulink modeling 提供實作藍圖，內含三件事——**實作標的**（可實作的方法一句話＋對應式號範圍）、**介面定義**（輸入／輸出／參數表：維度、單位、來源式號——直接供函式簽名與 Simulink port 設計）、**逐步實驗步驟**（編號步驟逐步引用式號/頁碼錨點，末尾附驗證點：與文獻數據／圖表對比的檢核）。一律以文字描述，**不畫圖**（方塊圖／流程圖屬工程師建模時的產物，不在筆記中預作）。無可實作內容的文獻（survey、純理論評述）寫「不適用（原因）」——保留章節以證明評估過。概念層演算法細節仍住原子筆記「演算法程序」，此處只引用不重複。
- 「可衍生的原子概念」每條格式：`- [[原子筆記名]]（中文名） — 一句話描述`；決定不建原子筆記的概念寫純文字並附原因，不留空的 wikilink。
- 若某文獻與主題僅間接相關、決定不衍生原子筆記，在「決策說明」一節記錄原因。

### 4. 萃取概念 → atomic note（原子筆記）

依階段〇的萃取判準從 source notes 提出概念清單（每條標注：關聯 RQ、涉及文獻、建議粒度），交使用者確認後逐一建立於 `notes/`，用 `templates/atomic-note.md` 模板。範例見 `references/example-atomic-note.md`——**動筆前先讀它**，以下規則都以該範例為準：

**結構與內容**

- **一則筆記只講一個概念**（原子性）。若寫著寫著出現第二個概念，拆出去。
- **命名用概念名稱本身**（英文技術術語為主，如 `Component Mode Synthesis (CMS).md`）；筆記內文以繁體中文為主、技術術語保留英文。
- frontmatter：`type: atomic`、`topic`、`cluster`、`rq`（關聯的研究問題編號，如 `[RQ1, RQ3]`）、`status: draft`、`verified: none`。
- 章節骨架：核心陳述 → 文獻回顧 → 爭議與歧異 → 符號表 → 數學形式 →（演算法/程序類概念加）演算法程序 → 關鍵要點 → 相關概念 → 來源。純定性概念可省略符號表與數學形式，但不得把公式塞回文字段落充數。
- 「相關概念」至少連結 1–2 則其他原子筆記，並一句話說明關係。
- 「來源」段回連 source note 並帶頁碼/章節。
- 同一概念出現在多份文獻時，把各文獻的觀點整合在同一則筆記（交互對照），不要一個概念多則筆記。

**衝突處理（v3 新增，交互對照的硬規則）**

- 「爭議與歧異」為**必要章節**：整合多文獻時，凡結論、適用條件、慣例（軸系、正負號、無因次化）不一致處，一律在此節並陳各方立場＋出處錨點，**禁止默默擇一**。
- 每條歧異須裁定其一：「已裁定（採 X，理由…）」／「未裁定（待使用者判讀／待更多文獻）」。未裁定項同步登錄到 MOC 的「待釐清 / 開放問題」。
- 無歧異時本節寫「無（已核對 N 份來源，結論一致）」——保留章節以證明檢查過，而非省略。

**符號政策（v3 新增）**

- 每主題建一則 `notes/{主題}-符號慣例.md`：載明本主題筆記統一採用的軸系、正負號慣例、無因次化方式與核心符號；各原子筆記遵循之。
- 原子筆記「符號表」採三欄：**本筆記符號｜原文符號（各文獻）｜意義**。與原文一致時原文欄寫「同左」；不一致（改記號、變號、轉軸系）時必須寫出對映與轉換說明——這是公式轉寫錯誤的第一道防線。

**撰寫風格（比照論文文獻回顧）**

- 「文獻回顧」一節以學術文獻回顧的口吻撰寫：以「作者 (年份) 提出／指出／證實」敘述，明確區分各文獻的貢獻、方法演進與彼此關係（誰奠基、誰延伸、誰驗證），論述問題設定的動機與方法的取捨理由；並引用 source note 的批判評估——對證據層級較弱的結論（如僅 L2 模擬）在行文中如實限定其效力。理論鋪陳要詳細嚴謹——寧可多寫兩段把前因後果講清楚，不要壓縮成條列。
- **公式與文本強制分離**：凡含等號、不等號或運算關係的數學式，一律獨立為 `$$…$$` display block 並以 `\tag{n}` 編號；行文中只允許出現單一符號（如 $\bar c$、$[M_R]$），禁止行內夾帶完整方程式。公式集中在「數學形式」一節，每條式前註明來源（文獻＋原文式號），行文以「見式 (n)」引用。
- 演算法／流程類概念另立「演算法程序」一節，以編號步驟寫出可執行的程序，步驟中引用式號。

### 5. 建 MOC＋綜合層（每主題一則）

用 `templates/MOC.md`，存於 `MOCs/`，命名 `主題-MOC.md`。除索引功能外，**v3 的 MOC 必含綜合層**——這是研究產出的精華所在：

- **研究框架**：階段〇確立的 RQ 與工程決策需求（無人值守時的假設也記在此）。
- **核心概念索引**：依理論脈絡（如：載荷來源 → 耦合 → 建模 → 驗證 → 最佳化）分節串接**全部**原子筆記，每條附一句話定位；文末回連全部 source notes。此結構同時就是階段二工程文件的大綱。
- **方法比較矩陣（v3 新增）**：當主題涉及多個可互相替代的方法／架構時必建。欄位依工程決策需求設計，基本欄：方法｜核心假設｜適用範圍｜驗證層級（取自 source notes 的 evidence_level）｜實作成本｜代表文獻。每格內容須可追溯（帶筆記連結或錨點）。
- **SOTA 評述（v3 新增）**：一至三段文字，回答每條 RQ 目前文獻能給出的最佳答案與其把握程度。
- **待釐清 / 開放問題（v3 升格為必填）**：收錄（a）原子筆記中未裁定的爭議、（b）RQ 尚未被現有文獻回答的部分。此節即 **scout 缺口陳述的直接輸入**——條目寫成可交給 scout 的缺口語句（「缺乏 X 條件下 Y 的 Z 證據」）。

### 6. QA gate（結構＋內容雙重驗證）

**結構驗證**——執行 `python3 <skill根>/scripts/check_vault.py <vault路徑> --source-dir <source路徑>`，錯誤（error）須全數清零，警告（warning）逐條判讀後回報：

| 檢查項 | 標準 |
|--------|------|
| 斷鏈 wikilink | 0 |
| 孤兒筆記（無入鏈的原子筆記） | 0 |
| 僅被 MOC 連入的原子筆記 | warning（連結密度不足，判讀是否補「相關概念」） |
| MOC 覆蓋率 | 全部 atomic + source notes 皆被 MOC 收錄 |
| 原子筆記出鏈（至其他筆記） | 每則 ≥1 |
| frontmatter 完整性 | 必填欄位齊全（含 bibkey、venue、evidence_level、rq） |
| source_file 路徑 | 指向實際存在的檔案（相對路徑比對；同名檔須完整路徑） |
| 重點摘錄頁碼錨點 | 每條摘錄含 p./§/Eq./ch. 等錨點（v3 機械檢查） |
| 必要章節 | source note 含批判評估＋涵蓋自評＋工程實踐（v3.1）；atomic note 含爭議與歧異（v3） |
| status ↔ verified 一致性 | `stable` 必須 `verified: content`（v3 機械檢查） |
| 公式紀律 | `$$` block 帶 `\tag`；行內 `$…$` 含 `=` 者列 warning（v3） |
| 未建檔文獻 | source/ 內無對應 source note 的檔案 = 0 |

**內容抽驗（v3 擴充為三軌）**：

1. **正確性抽驗**：至少抽 20%（最少 2 篇）source notes 回對 PDF 原文，核對頁碼錨點、公式（含正負號）、關鍵數據。
2. **公式全驗（原子筆記）**：凡含「數學形式」的原子筆記，升 `stable` 前其**全部**公式須逐條對照原文頁面渲染影像核對——公式是二次轉寫＋跨文獻整合的高風險區，不適用抽驗率。
3. **完整性抽驗**：對抽中的 source notes，以其「涵蓋自評」為基準對照原文，檢查有無「該萃取而未萃取、也未記錄不萃取原因」的重大遺漏（recall 檢查）。

發現錯誤即修正，並考慮同型錯誤是否散布在其他筆記（公式轉寫錯誤通常會複製到引用它的原子筆記）。

**status 升級（v3 與 frontmatter `verified` 綁定）**：

| status | 條件 | verified 欄位 |
|--------|------|---------------|
| `draft` | 初稿 | `none` |
| `reviewed` | 結構驗證通過 | `structure` |
| `stable` | 內容核驗通過（source note：正確性＋完整性；atomic note：公式全驗） | `content`（＋`verified_date`） |

只有實際驗過的才升級，不要整批升級。**筆記在升 `stable` 後被實質修改（新增/更動技術內容），status 降回 `draft`、`verified` 重設為 `none`**，重新走驗證。

### 7. 階段一收尾

以表格回報：文獻數、三類筆記數、triage 摘要、QA 結果（error/warning）、三軌抽驗發現與修正、未裁定爭議清單。**向使用者確認後才進階段二。**

## 階段二：obsidian/ → documents/

### 1. 開發稿（.md）

- 以該主題 MOC 的章節結構為大綱，把原子筆記內容整合成**連貫敘事**（不是筆記的堆疊——散點要串成推導鏈，段落間要有邏輯過渡）。MOC 的比較矩陣與 SOTA 評述直接轉化為文件的「方法比較」與「現況評估」章節；各 source note 的「工程實踐」節彙整為「實作/驗證」章的素材（v3.1）。
- 撰寫過程採用 doc-coauthoring skill 的共筆流程：先向使用者確認文件目的、讀者與詳略深度，分節起草、逐節迭代。（若未安裝 doc-coauthoring，改走一般分節迭代。）
- 標準章節（依主題增減）：目的與範疇 → 理論背景 → 方法/推導 → 方法比較與選型依據 → 假設與限制 → 實作/驗證 → 結論 → 參考文獻。
- **參考文獻由 source notes 的 frontmatter（bibkey、authors、year、title、venue、doi、volume_pages）機械生成**，不憑記憶補書目；內文重要陳述保留來源標註（作者年份＋頁碼），維持可追溯性。
- 引用弱證據層級（L1/L2）文獻的結論時，行文中如實限定效力；「假設與限制」章節須彙整沿用自各原子筆記的假設，不得只寫文件自身的假設。
- 產出 `documents/主題.md`，交使用者審閱迭代。

### 2. 交付檔（.docx / .pdf）

使用者確認 .md 定稿後，依交付需求轉檔：`.docx`（需簽核/追蹤修訂）用 docx skill，`.pdf`（唯讀交付）用 pdf skill。轉檔前先讀對應 skill 的 SKILL.md。

### 3. 停止點

交付 .docx/.pdf 後**本 skill 的工作即結束**。明確告知使用者：接下來由工程師判讀資料的取捨，後續是否產出互動 app 或正式研究報告屬另外的討論——不要主動接續做階段三。

## 增量更新程序（v3 新增）

vault 建成後補入新文獻時（含 scout 取檔回流）：

1. 新文獻先跑 `pdf_probe`（可只對新檔）取得分流 → 走 Pass 1 定位（併入既有 triage 表）→ Pass 2 依路由建 source note。
2. 觸及既有概念者，整合進**既有**原子筆記（不另建）；被修改的原子筆記依前述規則 status 降回 `draft`，並於筆記末「變更紀錄」一節追加一行：`日期｜併入 {bibkey}｜變更摘要`。新增歧異走衝突處理。
3. 連動更新 MOC：索引、比較矩陣、SOTA、開放問題（已被新文獻回答的條目結案並註明出處）。
4. 若該主題已有 `documents/` 產出：**不默默改文件**——在收尾回報中列出「文件受影響段落清單」（文件章節 ↔ 變更的筆記），由使用者決定是否改版文件。
5. 重跑 QA gate。

## 無人值守與大批量模式（v3 新增）

**無人值守**（使用者明示不在線、或排程執行）：各確認點不停等，改為「合理假設＋記錄」——所有本應請使用者裁定之處（RQ、概念清單、粒度、衝突裁定）記錄於 MOC「研究框架」與「待釐清」節，統一標注「未經使用者確認」，收尾時彙整成一張「待裁定清單」表格供使用者回線後批次裁定。衝突一律記「未裁定」，不代替使用者做研究判斷。

**大批量**（待處理 >10 篇）：Pass 1 triage 照常單流程完成；Pass 2 深讀可分群平行處理（各群獨立建 source notes），但**原子筆記整合、MOC/綜合層、QA gate 必須由單一主流程統一執行**——交互對照與衝突偵測不可分散進行。

## 品質原則（貫穿全程）

1. **可追溯**：任何寫進筆記或文件的技術陳述，都要能沿「文件 → 原子筆記 → source note → 頁碼」找回原文。做不到就別寫進去。
2. **批判而非轉錄**：每份文獻都要評估證據層級與適用邊界；每處文獻歧異都要並陳與裁定。研究者的價值在判斷，不在抄寫。
3. **不確定就標註**：OCR 品質差、公式看不清、原文語意模糊時，在筆記中明確標記（如「⚠ 原文掃描不清，符號待確認」），不要猜。
4. **語言慣例**：內文繁體中文，技術術語、法規名稱、變數符號保留英文原文。
5. **簡潔回報**：進度與結果用表格，避免冗長敘述。
6. **成本控制（v3.2 新增）**：token 是有限資源，讀取策略須刻意節制。硬規則——(a) 每份 PDF 先過 `pdf_probe` 分流，依 manifest 路由讀取，不自行改路；(b) 文字層優先，影像渲染是**例外**、只用於掃描件 OCR 與公式逐條核對的必要頁；(c) `large`（>200 頁）檔一律先章節定位再深讀，**絕不整份深讀或整份渲染影像**——單一大檔整份影像化即可燒掉一次額度。省 token 不是抄捷徑：分流與章節定位讓「該讀的精讀、不該讀的不碰」，品質與成本一起顧。
